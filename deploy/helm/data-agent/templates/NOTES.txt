Remember: the external backing services (ClickHouse, MCP, token IdP, OpenAI,
Couchbase, Neo4j, Redis, embedding/reranker APIs) are NOT deployed by this
chart. Confirm their endpoints in `config` are correct.

This chart renders NO Secret. Every workload mounts
`{{ include "data-agent.secretName" . }}` via envFrom; create it out-of-band
(vault / external-secrets / sealed-secrets) with OPENAI_API_KEY,
COUCHBASE_PASSWORD, NEO4J_PASSWORD, MCP_SERVICE_KEY, TOKEN_ISSUER_API_KEY,
EMBEDDING_API_KEY and RERANKER_API_KEY. Verify it exists — a missing Secret
wedges the pods in CreateContainerConfigError rather than failing loudly:

  kubectl --namespace {{ .Release.Namespace }} get secret {{ include "data-agent.secretName" . }}
{{- if .Values.components.hydrator.enabled }}

VERIFY MCP_SERVICE_KEY IS IN IT. The chart can no longer inspect the Secret, so
this is on you: the hydrator authenticates the MCP export routes with that static
service key (it has no user JWT), and with the key blank or absent it REFUSES to
start — neo4j is never seeded and every runtime pod fails its /ready gate
FOREVER. Check it, or disable the hydrator (components.hydrator.enabled=false):

  kubectl --namespace {{ .Release.Namespace }} get secret {{ include "data-agent.secretName" . }} \
    -o jsonpath='{.data.MCP_SERVICE_KEY}' | wc -c
{{- end }}

Rotating a key in that Secret does NOT restart the pods — the chart cannot see its
contents, so there is no checksum to change. Roll them yourself:

  kubectl --namespace {{ .Release.Namespace }} rollout restart deploy \
    -l app.kubernetes.io/instance={{ .Release.Name }}
{{- if not .Values.secrets.existingSecret }}

NOTE: `secrets.existingSecret` is unset, so the workloads reference the
conventional name above. Pointing it at the SAME Secret the data-agent-learning
release uses is the recommended posture — the shared Couchbase/Neo4j credentials
and the tenant identity they authenticate then cannot drift between the two
planes.
{{- end }}

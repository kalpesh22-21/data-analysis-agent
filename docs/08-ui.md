# 08 — UI

Trust is the product. The UI should make the agent's reasoning inspectable and give the user
correction surfaces that feed the learning loop.

> **Reconciliation note (2026-07).** A codebase audit found the runtime's entire HTTP surface is
> two SSE endpoints — `POST /turn` and `POST /turn/resume` — and the final `result` event carries
> only `{status, assistant_text, pending_question, tool_calls_made}` (`runtime/app.py`
> `_outcome_to_dict`). Most transparency promises below therefore need **backend surface work before
> any UI can render them**. Build direction is locked: **enrich the `/turn` result event first**,
> then build the panels that read it. Prerequisites are collected in
> [Backend surface prerequisites](#backend-surface-prerequisites); each principle below is tagged
> with what it depends on.

## Principles

- **Stream the plan + the SQL.** Always show the query that ran; let users expand results as
  table/chart. Transparency is what makes the agent a trusted teammate. *(Depends on: enriched
  result event — the SQL string(s) + result table are not on the wire today.)*
- **Stream task/progress, not just the final answer (D61).** A turn runs an embed + recall + rerank +
  **two LLM round-trips** (pick blueprint, then the D56 verify gate) + queries — easily several
  seconds. The UI shows **live step-level progress** ("searching for a matching blueprint…", "running
  query…", "step 2 of 4: department actuals…", "verifying results…") so **perceived latency ≪ total
  latency**. Progress events are the same stage boundaries the [10](10-observability.md) spans emit
  (one instrumentation, two consumers). **PII-safe:** progress shows **step/shape, not cell values or
  bound slot values** (D25). "Time to first progress event" is the felt-latency metric. *(The
  `progress` SSE event — `{step, shape}` — already ships; this principle is honored today.)*
  - **LLM-generated progress summaries (opt-in — `progress_summary_enabled`, a gated D25 relaxation
    for this channel only).** Off by default. When enabled, the agent loop runs a small/cheap side LLM
    (`openai_summary_model`, default `gpt-4.1-mini`) over each tool **CALL** (tool name + arguments —
    **never results**) to mint a natural-language, present-tense line ("Querying overtime pay by
    department for the January period") streamed to the UI as a normal `progress` event. It arrives
    **additive** to the instant `running <tool>…` template label (fired the moment the tool
    dispatches) — the summary enriches, arriving when ready; if it is slow, fails, or is cancelled at
    turn end, the template label simply stands. The summarization is **fire-and-forget and
    non-blocking**: it is scheduled concurrently and never awaited before dispatch, so it can never add
    latency to the tool or delay the turn result (bounded tokens + a `progress_summary_timeout_seconds`
    timeout; fail-soft — a summarizer error never breaks a turn). **Deliberate, gated D25 relaxation
    for THIS channel:** with the flag on, `progress.step` **may contain a value-rich line** that
    includes concrete parameters drawn from the tool arguments (a period, a department) — this relaxes
    the "no cell/slot values in progress" rule for the progress-summary channel and is why it is
    opt-in. The relaxation is confined to `step`: the machine-readable **tool name stays in
    `shape.tool_name`**, and `shape` remains governed by the `_SHAPE_ALLOWLIST` (no other values leak
    into `shape`). The value-rich `step` bypasses the static `_STEP_LABELS` table and is used verbatim,
    not templated. Requires an OpenAI key; absent the flag or the key the feature is inert and the
    stream is byte-identical to today.
    - **What the relaxation admits: business values, never internal database structure.** The
      summarizer is shown a **per-tool allowlisted projection** of the arguments, default-deny: nothing
      at all for a tool that is not explicitly listed, and never `sql`, `database`, `table` or `column`
      for any tool. `runQuery`/`listTables`/`getTableSchema`/`sampleRows` therefore contribute their
      **name only** ("running a query against the warehouse"), while `runBlueprint`'s slot values, the
      search tools' `query` and `resolveValues`'s `concept` pass through — those are the values the
      relaxation exists for. A produced line that repeats an identifier drawn from the *withheld*
      arguments (a `db.table`, a table name) is discarded in favour of a static safe line for that
      tool — as is one that merely *looks* structural (a qualified or quoted identifier, a
      snake_case/PascalCase token, SQL), whatever its provenance, since the allowlisted free-text
      values are authored by the schema-aware main model. The model instruction says the same thing;
      the projection and the shape check are what enforce it.
    - **Ordering caveat (no data leak).** The summary is minted from the CALL (the model's own
      requested tool + args) and fires the moment the tool dispatches — *before* any access-control /
      scope denial is known. So on a denied call the UI can show the value-rich line ("Querying
      salaries by department…") immediately followed by "step denied: runQuery". This is expected and
      leaks nothing: the line derives only from what the model itself asked for (never from warehouse
      results, which the model never received), so it exposes no data the caller isn't already driving.
- **The answer speaks business, and the runtime enforces it (ISSUES I1).** The same
  no-disclosure rule the prompt asks for above is now also applied to the OUTPUT: every piece of
  model prose that reaches a user — the no-tool-calls answer, the `answerWithTable` `answer`, the
  partial text carried on a pause, and the `askUser` question — is scrubbed of identifier-shaped
  tokens on the way out (`runtime/answer_scrub.py`, called once per exit inside
  `AgentLoop._finish`, so the live answer and the persisted message are the same string and
  `/session/history` can never disagree with what the user was shown). A qualified name, a
  `snake_case` token or a quoted identifier becomes **`[schema detail withheld]`**; a blueprint or
  knowledge id becomes **`[saved analysis]`** — visible markers, never a silent deletion, so a user
  can see that something was withheld and ask. Detection is by identifier **form**, never by word
  list: "the Department column is free text" and "Sales has 3 people. Engineering has 2." are
  correct business answers and survive byte-identically. There is **no flag and no refusal** — the
  turn always completes, redacted, which is deliberately stricter than the answer-shape gate (that
  one can exhaust its allowance and let prose through; this one cannot).
  - **The structured payload is deliberately NOT scrubbed (the I2 decision).** `sql_executed`,
    `answer_sql`, `answer_tables[].sql`, `answer_tables[].caption`, `blueprint_use` and
    `verification` keep naming exactly what ran. An answer may therefore read "I used [saved
    analysis]" while the blueprint chip beside it names the id, and that divergence is the design:
    prose is the agent's VOICE, those fields are the AUDIT SURFACE the transparency principle at the
    top of this list exists for. Do not reconcile them.
- **Surface blueprint use.** When a validated blueprint runs, show
  `Using blueprint avg_salary_by_dept · period=2026-05 · department=all` with filled slots visible.
  Builds trust and gives a correction surface. *(Depends on: enriched result event — the
  blueprint-use descriptor.)*
- **Surface a passive verification badge.** The D56 grain/invariant gate runs on the **blueprint fast
  path** — **not** on raw-loop answers, and a *failed* gate degrades to the raw loop rather than
  returning a failed answer. A blueprint-verified answer carries a quiet **"verified ✓"** badge —
  **never a pause, never a prompt**. **Absence of the badge means the answer came from the raw loop
  (unverified) — not that verification failed;** a `passed:false` badge never reaches a user.
  Verifying *every* answer would require a new raw-loop gate (out of scope — tracked separately).
  *(Depends on: enriched result event — the verification-status field. Semantics locked in
  `docs/decisions/ui-slice1-enriched-result-contract.md` §6.)*
- **Show lineage — what the answer read.** After an answer, show the USES-set: which
  `database.table.column`s the answer actually touched. See [Provenance / lineage](#provenance--lineage).
  *(Depends on: provenance read endpoint.)*
- **Inline clarification chips.** Catalog ambiguities (`salary → base_salary | gross_pay`, with the
  `clarify_if "take home"` rule) render as one-tap disambiguation, not a paragraph.
- **External dataset upload** with a column-mapping step (which column is EmployeeCode / DepartmentCode).
  *(Depends on: file-upload + column-mapping loader — see prerequisites.)*
- **Review inbox** for the learning loop's gated outputs — the surface where a human keeps the flywheel
  clean. Fully reconciled to the code in [Review inbox](#review-inbox).

## The enriched turn-result contract

**Locked build direction:** enrich the `/turn` `result` event *before* building the UI panels that
consume it. This is the backend work that precedes the UI.

**Today (`runtime/app.py` `_outcome_to_dict`):**

```
result: { status, assistant_text, pending_question, tool_calls_made }
```

**Target contract** — the same event, additionally carrying:

| Field | Payload | Renders as |
|---|---|---|
| `sql` | the SQL string(s) that ran this turn | the "show the query" panel |
| `result_table` | columns + a preview slice of rows | expandable table (→ chart, lib TBD) |
| `blueprint_use` | `blueprint_id` + filled/bound slots | the `Using blueprint …` chip |
| `provenance` | the USES-set — `database.table.column`s the answer read | the [lineage](#provenance--lineage) panel |
| `verification` | the D56 gate pass/fail | the passive **verified ✓** badge (never a pause) |

These are a **target contract**, not current behavior. Honoring them requires **threading data from
the session trail / blueprint executor onto the result event** — the SQL and result table live in the
tool trail, `blueprint_use` in the blueprint executor, `provenance` in the per-turn USES-union
(`TurnMessage.provenance`), and `verification` in the D56 gate outcome. None is on the SSE wire today;
the existing `ui/static/index.html:280` TODO ("SQL/results need a richer result payload from the
runtime SSE") marks exactly this gap. **Backend work precedes the UI.**

## Key flows

### Ask → answer (fast path)
1. User asks. 2. Thin blueprint cards considered (invisible). 3. On the **blueprint fast path**, the
validated blueprint runs and passes the agent-side verification gate (D56 — code-computed
grain/invariant assertions) *before* its answer is returned; a **failed** gate does not surface a
failed answer — it **falls back to the raw loop**, which answers **without** that gate. The user is
**never asked to verify**. 4. Answer + SQL + result + "Using blueprint …" chip, and — **on the
verified blueprint path only** — a passive **verified ✓** badge. Verification never *pauses*; it is
mandatory **on the blueprint path** (no silent skip there), but a raw-loop answer is simply unverified
(no badge). *(Steps 3–4 render from the enriched result event.)*

### Ask → clarify → answer
`askUser` pauses the loop and renders a chip or free-text prompt; the answer resumes the turn
(`POST /turn/resume`). Fires only on the disciplined triggers (catalog `clarify_if`, missing required
slot, low confidence, expensive/broad query). Otherwise the agent uses a **default + states the
assumption** as a one-tap "actually, I meant…" correction.

### Provenance / lineage
After an answer, show **which tables/columns the answer read** — the USES-set. This is the near-term
transparency surface: "trust is the product," so a lineage panel belongs next to every answer.

- **Source:** the per-turn provenance union stored on `TurnMessage.provenance`, itself the union of
  per-tool-call `TrailEntry.provenance` (`sqlparse/provenance.py:528` extracts the column USES-set
  from SQL; `runtime/provenance/capture.py:59` captures it per successful tool call).
- **Shape:** a set of `database.table.column` references — governance-internal today and **redacted
  from spans** (D25), so it is not currently exposed to any client.
- **Depends on:** a **provenance read endpoint** — the union is stored but has no read surface a UI
  can call.

### Upload → join
Upload file → map key columns → agent joins scratch table to HR data → answer. *(The scratch-materialize
plumbing exists — `runtime/mcp/scratch_client.py` — but takes already-parsed rows; there is no
file-upload front door or column-mapping API yet. Depends on: file-upload + column-mapping loader.)*

### Correction → learning
Any user correction (chip flip, "actually I meant…", thumbs) is captured into the session trail and
becomes input to the end-of-session write router.

### Conversation transcript
The current UI shows only the **latest** answer. Specify a **multi-turn transcript view** so a
conversation reads as a conversation: prior turns (question, answer, SQL, lineage) stay visible as the
user refines intent. Follow-ups already carry full context **server-side** (Couchbase), so the
transcript is a client-side rendering concern over turns the session already retains — no new
server-side memory is required, but rendering prior turns' SQL/table/lineage inherits the same
enriched-result dependency as the latest turn.

### Login & auth
On successful login the **UI's backend** obtains a signed JWT for the session (via `token_service`'s guarded `POST /token`, or an external IdP in production). The browser receives the JWT; it does **not** sign tokens itself. Simultaneously, the UI generates a fresh `session_id` (per D81).

**Current default — all-column access (interim, D82/D80):** every JWT is currently minted with `column_scope: []`, which means no column restriction. Per-user column entitlements are not yet wired; row-level tenant isolation still applies at the warehouse independently.

Every turn, the backend forwards the JWT (Bearer) + `X-Session-Id` to the MCP. The model never sees the JWT, scope, or `session_id` (D5).

## Review inbox

The inbox is where a human keeps the flywheel clean. Reconciled to the code below.

**Candidate type is a closed enum** (`learning/extractor/models.py:20`):
`blueprint | global_knowledge | user_knowledge | schema_edit`. The inbox differentiates items not by
type alone but by a **re-derived `reason`** (`learning/inbox/models.py`;
`derive_inbox_reason` in `learning/writer/routing.py:100-116`) — re-derived from the same routing
rules the writer used, so the label can never drift from the decision that produced it.

**Status state machine** (`candidate/models.py:23-32`) — this **replaces** the spec's old
"pending / approved / retracted" wording:

```
extracted → candidate → in_review → validated → quarantined → rejected → retired
```

Human decisions are the only caller-driven transitions:

| Action | Transition | Meaning |
|---|---|---|
| approve | `in_review → validated` | knowledge becomes retrievable; blueprint confirmed; `schema_edit` opens the D53 PR |
| reject | `in_review → rejected` | archived as a **negative training signal** (D29) — not a delete; the row is retained for the learner |
| retract | `validated → retired` | post-promotion pull-from-index (a leak/drift pull) |

**Reviewer-facing projection.** The inbox lists `InboxItem` (`learning/inbox/models.py`), a projection
**derived** from an `in_review` candidate — not stored. It carries a **redacted `payload_view`**:
entity-bearing leakage spans are stripped (the entity value replaced) so the reviewer sees *what* leaked
(field + kind) without the raw value re-leaking through the inbox (D17). Raw evidence quotes are **not**
inlined — the item carries `evidence_refs` (KV keys) the reviewer uses to fetch quotes from the
`learning_audit` store **separately**. Document this redaction rule in the UI: the inbox never re-exposes
a value the leakage gate flagged.

**Inbox categories** (each a re-derived `reason`):

| Category | Type | Reason | Notes |
|---|---|---|---|
| Global-knowledge pre-gate **(flagship)** | `global_knowledge` | `knowledge_pre_gate` | always `in_review`; the D58a human-approval-*before*-retrievable gate |
| Schema-edit proposal | `schema_edit` | `schema_edit` | human pre-gated; approve opens the D53 PR (merge is the real gate) |
| Blueprint dedup conflict | `blueprint` | `dedup_conflict` | a SOFT near-miss (`action` = `conflict`/`merge`) — **replaces** the old "blueprint variants" |
| Suppressed duplicate | `blueprint` | `suppressed_duplicate` | a DETERMINISTIC match (`action` = `increment`) against a **live** learning artifact; its `hit_count` was incremented and the row is kept only so a human can revise a genuine delta. A duplicate of a *terminal* (rejected/retired) artifact, and a candidate identical to an MCP canon blueprint, are DROPPED at S6 and never appear here |
| Mined blueprint candidate | `blueprint` | `blueprint_sampled` | human review (100% default sample) |
| Leakage near-miss | `blueprint` | `leakage_near_miss` | entity-leak detection edge case |
| Routing fallback — review required | `blueprint`/other | `fail_to_review` | **fail-closed:** anything uncertain lands in review rather than auto-committing — the fail-closed guarantee made legible to reviewers |
| Parameterization form | `blueprint` | `needs_parameterization` | the merit-passed candidate whose literals could not all be classified; the reviewer **completes the form** rather than adjudicating the idea (`learning-declined-candidate-review.md`) |
| Judge retry (not listed) | `blueprint` | `awaiting_judge` | durable internal retry state; after 24 hours it becomes a parameterization form marked `judge_unavailable` rather than disappearing |
| Hand-authored blueprint | `blueprint` | `hand_authored` | written by an expert at `/mint`. **Not a defect** — it is why the row exists: a hand-authored blueprint has no session behind it, so it is never auto-landed |
| Contradictory-knowledge flag | — | — | **FUTURE — NOT IMPLEMENTED.** Requires a contradiction-detection candidate type + reason before the inbox can surface it. Closest mechanism today is the negative-signal path (reject→`rejected` retained as training signal; `apply_user_correction` demoting validated blueprints). |

> **No "variant"/"version" concept exists in the code.** The old spec's "blueprint variants" is
> removed; blueprint collisions are `dedup_conflict` (near-miss) or `suppressed_duplicate`
> (deterministic match), not versions.

> **`user_knowledge` is excluded.** It is **auto-committed per-user** and does **not** enter the
> review inbox — a reader should not assume it does.

**API surface.** The in-process API a future inbox endpoint wraps is
`ReviewInbox.list / approve / reject / retract` (`learning/inbox/inbox.py:65-131`). There is currently
**no HTTP or CLI surface** for it. A **thin inbox service endpoint** is required backend work before any
review UI can call it.

> **Open backend item — CONFIRMED GAP (2026-07-09).** Approved `global_knowledge` has **no retrieval
> landing path**. Approval only flips `status → validated` in the `learning_candidates` KV store
> (`promotion/scheduler.py:414-420`); the runtime recalls knowledge from Neo4j `:KnowledgeChunk` nodes
> (`retrieval/vector_index.py:128-174`), which **only** the offline fixture seed
> (`scripts/seed_neo4j_corpus.py`) ever writes. `CorpusLandingWriter` is blueprint-only — there is no
> `knowledge_seed_from_candidate`. So **"approve → retrievable" does not hold for `global_knowledge`**
> despite `leakage/gate.py:58` / `routing.py:25` asserting it does; no test catches this (the approval
> test asserts only `status=="validated"`). **Must be fixed before the inbox UI ships an approve action
> for global_knowledge** (otherwise the flagship inbox action is a silent no-op). Fix mirrors the
> blueprint path: add a `knowledge_seed_from_candidate` mapping + a land-into-Neo4j branch in
> `apply_human_decision`'s non-blueprint path (land **before** writing `VALIDATED`), plus a
> write→recall test. No live impact today (loop is dormant, `LEARNING_ENABLED` off).

## Session handling
The UI **generates `session_id`** and sends it (with JWT + scope) on every request. Follow-ups carry
full context server-side (Couchbase) so users can refine intent without restating. See
[Conversation transcript](#conversation-transcript) for surfacing this as a multi-turn view.

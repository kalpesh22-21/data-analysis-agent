## Findings from the wiring check

Five things the spec assumes that the code either already provides or does not. Each is expanded in its own doc.

1. **Card enrichment is a Cypher `RETURN` change, not N extra fetches.** `_RECALL_QUERY` (vector_index.py:158) selects only `id, intent, slots_summary, uses, score`, but `resolves_json` / `slots_json` / `result_grain_json` are already stored on the `:Blueprint` node. Adding them to the projection costs nothing per call. → [02](02-blueprint-card-enrichment.md)
2. **`status` is redundant on a search card.** Recall already filters `coalesce(node.status,'validated') = 'validated'`, so every recalled card is validated by construction. The spec lists it as an enrichment field; it carries no information there. → [02](02-blueprint-card-enrichment.md)
3. **`SessionStore` is a `Protocol` with two implementations.** The new fields touch the protocol, `CouchbaseSessionStore`, `InMemorySessionStore`, `SessionDoc.to_doc`/`from_doc`, and `test_couchbase_connect_gate.py` (which auto-parametrises over every public coroutine) — five places, not one. The store API must take a **merge callback**, not a precomputed value: `_mutate_with_cas_retry` re-runs its callback on conflict, so a value computed from a stale read would clobber the winner. → [03](03-analysis-state.md)
4. **The finalization nudge on exit #1 cannot be a standalone tool message.** `_assembled_to_canonical` only emits a `tool` message by expanding a trail entry into an `assistant(tool_calls) + tool` pair. Fabricating such a pair is itself an established pattern (discovery emulation does it), so the reason to avoid it is narrower: the nudge answers no call, and a fabricated pair would need re-splicing, deduping and pinning every rebuild for something that should live one round-trip. Use ephemeral `user`-role injection — same splice site and never-persisted posture as `discovery_canonical`, but **one round-trip, not one window**. → [05](05-finalization-enforcement.md)
5. **The §5.1 late-init boundary is order-sensitive within one response.** Dispatch walks `capped_tool_calls` in array order, so the spec's own round-1 pattern (`updateAnalysisState` + 3 × `runBlueprint`) self-rejects if the model emits the blueprints first. Needs an intra-batch ordering rule — and the partition must run on the **raw** list, since capping silently discards the overflow. `askUser` short-circuits the whole batch before dispatch, so state calls must also be committed before a pause. → [03](03-analysis-state.md)

## Findings from the code review of 03 and 05

A review pass over the two coupled documents found the four defects with the widest blast radius. (03's and 05's own corrections tables record ten and twelve respectively; these are the ones that would each have shipped a silently-broken implementation.) All are fixed; recorded here because they are the kind of thing a reader re-derives.

6. **`analysisState` had no turn gate.** A state persists after its turn ends, so without `state.turn_index == turn_index` a stale `pending` intent from an abandoned turn refuses an unrelated later turn, burns its nudge, and writes `ENFORCEMENT_EXHAUSTED` onto the old turn's record. The predicate `live_analysis_state` is now defined once in [03 §A.1](03-analysis-state.md) and used by 03, 04 and 05. The original justification for keeping the field across turns — "`session_history` reads it" — was simply false.
7. **The finalization nudge counter reset on every resume.** `_run_loop_body` re-enters on `askUser` and blueprint resumes while `window_count` stays frozen, so a counter local to that function makes forced re-rounds unbounded. It is now persisted on `SessionDoc`, keyed by window, and consumed **per round-trip** rather than per refused call — two `answerWithTable` calls in one batch would otherwise burn both chances without ever granting a re-round. → [05 §C](05-finalization-enforcement.md)
8. **A forced re-round was free.** Exit #1 sits before `guard.record_iteration`, so looping back without charging the window leaves the 60-second wall clock as the only backstop — and every resume restarts it. → [05 §C.3](05-finalization-enforcement.md)
9. **The cross-turn drop closed the rendered block but not the trail entry.** `_is_stale_assumptions_entry` is hard-coded to one tool name, while every `updateAnalysisState` call leaves a `TrailEntry` whose `args` carry the descriptions with `frozenset()` provenance — kept under any `column_scope`, in every later turn. The predicate is generalised to a tool set. → [03 §D.1](03-analysis-state.md)

## Findings from the review of 01, 02, 04, 06 and 07

A second pass over the remaining five found four more of the same class.

10. **Emitting an event does not publish its payload.** `_GUARDRAIL_OBSERVER_ATTR_ALLOWLIST` (`observability/tracing.py:598`) is a strict attribute allowlist — deliberately not a type filter, because a bare `isinstance` check once leaked `loop_paused_ask_user`'s `question`. Of every payload key doc 06 proposed, **only `window` is on it**; the rest would reach Phoenix as correctly-named spans carrying nothing. Different mechanism from `OTLP_DROP_SPAN_NAMES`, which filters names one layer later. → [06](06-telemetry.md)
11. **Enrichment changes the search card's D44 posture.** `searchBlueprints` carries safe-empty `frozenset()` provenance *because* its cards hold no column identifiers; `resolves` and `result_grain` are column names, so enriched cards would be kept in replay forever under any scope. Resolved by setting the entry's provenance to the union of the returned cards' `uses`. → [02](02-blueprint-card-enrichment.md)
12. **The evidence trail cannot be handed in from the loop.** `_run_loop_body`'s only trail load sits *above* the round-trip loop and is reduced to signatures — a snapshot from there holds nothing from the current window, so every citation would fail as "unknown id" while looking correctly wired. The tool reads the trail itself. → [04](04-evidence-validators.md), [03 §C.1](03-analysis-state.md)
13. **A scripted model cannot prove routing.** `ScriptedModelClient.send_turn` never reads `messages`, so a suite built on it passes identically against a hostile prompt — and deliverable 01 changes nothing but a string. Resolved by splitting into a scripted runtime-mechanics suite (CI) and a **live-model routing suite that gates the release**. → [07](07-evaluation.md)

## Findings from the code review of the implementation

Four more, found reviewing the shipped code rather than the docs. The first is finding 9's class for the third time.

14. **The finalization refusal was the missed third carrier of finding 9's leak.** It is persisted as an `answerWithTable` entry — `denial_detail` naming every pending intent, `args` holding the refused draft prose, `frozenset()` provenance — so it replayed in every later turn of the session under any since-narrowed scope, telling a later turn to resolve **dead intent ids** with `updateAnalysisState`. `_is_stale_model_text_entry` now matches on error code as well as tool name. **05 §I's recorded rationale was itself inverted** ("the status gate is belt-and-braces; provenance is binding"): the status-gated current-turn exemption is provenance-blind, so `frozenset()` was load-bearing only in the later-turn contexts where the entry should not survive. → [03 §D.1](03-analysis-state.md), [05 §B.1](05-finalization-enforcement.md)
15. **`finalization_blocks` was keyed by budget window alone**, while `window_count` restarts at 1 on every external turn and the map is never cleared — so the forced re-round was silently dead from a session's second block-spending turn onward, writing `ENFORCEMENT_EXHAUSTED` for intents never asked twice and inflating 07's headline rate. Keyed by `(turn_index, window)`. Finding 6's class, one field over. → [05 §C.1](05-finalization-enforcement.md)
16. **An `askUser` past the per-iteration cap stopped pausing the turn** — a Release-1 regression: the scan moved onto the *capped* list when the state partition was introduced, and capping silently discards the overflow. The model's clarifying question was swallowed and the turn finished `done`. → [03 §E.2](03-analysis-state.md)
17. **Two unbounded/uncontained paths.** `claim_finalization_block` could raise out of `_run_loop_body` with the answer in hand (now caught, reported on `loop_finalization_block_claim_failed`, treated as "no re-round"), and surplus `updateAnalysisState` calls each cost a store write with no bound on the list (now bounded at two rejections, then dropped). → [05 §B.1](05-finalization-enforcement.md), [03 §E.2](03-analysis-state.md)

**One finding escalated past the docs, and the Lead has now ruled on it.** Evidence-backed blocking stops the model *asserting* an unfalsifiable reason; it does not stop it *producing* a falsifiable one. `SELECT … WHERE 1=0` yields `REQUIRED_DATA_UNAVAILABLE` — and `NO_ACCESS` costs **one metadata call**: `getTableSchema(<scratch_db>, <anything>)` fails closed with `SCRATCH_SESSION_VIOLATION` without touching data or locking the late-init boundary. Separately, zero rows is *also* how a correct query answers "nobody", so the block predicate fires on honest work.

## Findings from the first live run

18. **`analysisState` was completely non-functional in the real runtime, with the whole suite green.** `SessionStore` has **four** implementations, not two: besides `memory_store` and `couchbase_store`, both launchers wrap the real store in a hand-written `_LazyCouchbaseSessionStore` proxy that re-declares and forwards every method (`acouchbase` connects eagerly and needs a running loop; the launchers build their app at import). Release 1 added `apply_analysis_state` and `claim_finalization_block` to the Protocol; [03 §B](03-analysis-state.md#b-persistence) enumerated *five files* and *two implementations*, so neither proxy was touched. Every `updateAnalysisState` call on the real server raised `AttributeError` → `RUNTIME_TOOL_INTERNAL_ERROR`, and nothing in `tests/` could see it because nothing imports `scripts/`. **This is the same class as findings 6, 9 and 15**: a guard (here, a change list) derived from a hand-enumerated set rather than from what the contract requires. `read_full_result` had already been lost the same way once. Fixed by adding the methods *and* by `tests/runtime/test_launcher_session_store_proxies.py`, which derives the required surface from the Protocol and the proxy population from the source tree, so the next Protocol addition cannot be forgotten in either place. → [03 §B](03-analysis-state.md#b-persistence)
19. **The new prompt's no-finalize line suppressed `answerWithTable`, leaving the user a truncated markdown table in prose.** Across 11 live sessions, exactly two turns pasted a multi-row table into ordinary prose instead of calling the tool — `50d1ae74` (5 table lines, trail ended at `recordAssumptions`, 3 rejected `updateAnalysisState`) and `e2d24be3` (4 table lines, 7 rejected). Every turn with **no** `analysisState` activity used `answerWithTable` and described the table instead of reproducing it. `answerWithTable` **is** finalization, so *"Do not finalize while a tracked intent is unresolved"* told a model with open intents to avoid the terminal call — and prose is gated by nothing. Both turns also had every state init rejected, so `analysis_state` was `null` and the runtime's finalization enforcement never engaged either: **the instruction suppressed the correct behaviour while the safety net was off**, making the outcome worse than before Release 1. Same class as finding 16 — a new rule silently overriding an older one that nothing asserted the primacy of. Fixed by rescoping the line to *resolve your intents before finishing* (an unresolved intent is reported **in** the answer) and by stating the multi-row rule as unconditional. → [01a §5](01a-prompt-draft.md)

20. **Completion-by-citation never once worked against a live model: 9 attempts, 0 successes.** Measured across two sessions *after* the payload-normalisation fix, so the state really existed and the model really tried. It cited, in order, the blueprint id (`bp-active-headcount-by-department`), the tool **name** (`runBlueprint`), a **hallucinated** `call_UUGw4Mtd…`, and finally `""` — while the real `tool_call_id`s were in its context throughout (`context/budget.py` renders them on every trail entry; `_tool_trail_entry_to_canonical` puts them on the synthetic assistant message). One session burned 5 of its 10 tool calls on rejected completions and never produced an answer. **Every instinct the model showed was semantic**, so the binding moved to the moment the work is dispatched: `runQuery`/`runBlueprint`/`getTableSchema` take an optional `serves_intent="i2"`, stripped before dispatch and persisted on `TrailEntry.serves_intent`, and completion carries no evidence field at all — the runtime resolves the id and runs it through **04's own validators**, so every condition still binds. Explicit citation is kept, not deprecated: a tag is single-valued and cannot express ONE call answering SEVERAL intents, which [04 §A](04-evidence-validators.md) deliberately permits. Same class as findings 12 and 18 — a mechanism that looked wired, passed its whole suite, and could not be executed by the actor it was written for. → [01a §6](01a-prompt-draft.md)
21. **The routing bullets left no path to USING a pre-injected blueprint card: 7 of 7 blueprint turns searched first, 0 used a card directly.** Bullet 1 said an offered card is "often the answer"; bullet 2 said to call `searchBlueprints` **whether or not** one fits. There was no route from *"this card IS the answer"* to *"run it"* — bullet 2 intercepted unconditionally, and the model was obeying, not ignoring. Cost across 13 turns: 20 `searchBlueprints` calls / 52 recalls / 50 reranks / 40 embeddings, plus a pre-injected block (3 enriched cards + knowledge chunks, larger since 02) pinned in the current-turn region on **every** round-trip while never being acted on. This is an **overcorrection of finding-era 01**, whose fix to the old *"If none of the blueprints offered to you fit…"* fallback framing was correct and is preserved — but which also deleted the direct-use path; [01a §4](01a-prompt-draft.md) predicted the *opposite* failure, so that risk note is amended too. Fixed by making the split MECHANICAL: the cards are recalled from the whole question as one string, which is exactly the right query for a SINGLE deliverable (run it) and the wrong one for several (search per deliverable). Both paths now have their own contract test, so a future edit cannot collapse one into the other again. → [01a §7](01a-prompt-draft.md)

22. **The model was choosing and running blueprints on an authored prose sentence, never on the SQL — and nothing in the release could catch a mismatch.** A card (pre-injected or searched) carries `intent`, `slots`, `resolves`, `result_grain`. It carries **no SQL**, by design (02). So the whole blueprint route rested on the `intent` string being a truthful description of the query stored underneath it, which is a corpus-authoring property, not a runtime one. When the two disagree the model runs the wrong analysis and reports the number confidently. **The D56 grain gate does not cover this**: `verification: {method: blueprint_gate, grain_checked: true}` verifies the result SHAPE against the blueprint's own declared `result_grain` — it says the blueprint did what it claims, never that what it claims is what was asked. The prompt already carried the general form of the rule (*"Success is not proof of correctness: a query that runs proves the SQL was valid, not that it measured what was asked"*) with no concrete practice attached on the blueprint route, because there was nothing for the model to check against. **Decided by the user:** the model must call `getBlueprint(id)` and read the definition before `runBlueprint`, and the runtime refuses the run otherwise (`BLUEPRINT_DEFINITION_NOT_READ`, retryable, turn-scoped). Same class as findings 12, 18 and 20 in one respect only — a mechanism that passed its whole suite while the actor it was written for could not do the thing it assumed. **This partially reverses a saving 02 claimed; the reversal is recorded in 02's own terms** — per-candidate selection still costs no `getBlueprint`, the run itself now does. → [02](02-blueprint-card-enrichment.md#the-partial-reversal-getblueprint-before-runblueprint)

23. **The repeated-read guard told the model "you already have this" about results the budget had deleted — and the prompt's escape from it was welded shut.** Found while building finding 22's blueprint gate, then **proved by driving a real trim** rather than by reading the code: with `request_token_budget` set and the pair unpinned, a second `getTableSchema` was deduped *after* `fit_request_to_budget` had dropped the first one's pair from the rebuilt window (`MCP dispatches: 1, guard fired: 1, budget trimmed: 2`). The guard fires off `seen_read_calls`, which is seeded from the **persisted trail** — and the trail is not the rendered window. So the model held a data-free nudge pointing at a schema it could not read, with **no move available that recovered it**: re-asking produced the same nudge. Worse, `prompts.py` had told it *"Fetch it again only if it was summarized away and you can no longer read it"* — an instruction the guard made impossible to obey, and which named a mechanism (summarisation) that does not exist in this phase; the real one, budget trimming, went unmentioned. **The guard's contract is now stated precisely:** *an identical repeat is deduped **unless its result is no longer readable**.* Applied uniformly across `IDEMPOTENT_READ_TOOLS`, since the predicate is a property of the context rather than of any tool; bounded at two re-fetches per signature per window, because fetch → trim → re-fetch → trim is in aggregate the exact waste the guard exists to prevent, and the cap biting is emitted as `loop_trimmed_read_refetch_capped` — the signal that a turn is thrashing. Same class as finding 9 and finding 14: a rule whose stated premise ("it is in the history above") was true of one data structure and quietly false of the one that mattered. → [read_guard.py](../../../src/data_agent/runtime/loop/read_guard.py), [04 §condition 5](04-evidence-validators.md)

    **Two things this exposed that are worth keeping in view.** (a) The narrower **scope** route into the same hole is *already closed* and was closed the same way once before: `getTableSchema` was moved into `_NO_PROVENANCE_TOOLS` precisely because a restricted scope used to drop a fetched schema and leave the model "seeing the repeated-read guard's 'you already have this' nudge with no schema anywhere" (`provenance/capture.py`). The identical symptom returned through the **budget** door instead. (b) The deeper question — *if a schema keeps being trimmed, should it be pinned or summarised rather than dropped and re-fetched?* — is **not** addressed here and is deliberately out of scope; see *Follow-up: pinning versus re-fetching* below.

24. **`answerWithTable` succeeded on 6/6 single-deliverable turns and 1/9 multi-intent ones — and the first fix for that made a multi-intent turn strictly worse.** The tool carries ONE `sql` or `blueprint_id` (a multi-table payload was deliberately deferred), so the prompt was the whole lever, and it was pulled too hard: *"SAME GRAIN MEANS ONE QUERY: headcount by department and average salary by department are both per-department — write ONE query returning them side by side."* Measured on the next live three-part turn (*headcount by department, average salary by department, hires in the last 6 months*): `runBlueprint ×2 + runQuery ×1` over 7 rounds became **`runQuery ×3` + `runBlueprint ×1`**, timed out at 73s, and returned **no answer** with all three intents `pending`. Every `runQuery` was tagged `i1`, iterating on a join to merge two intents **two blueprints had already answered**. **The rule contradicted another rule in the same prompt, verbatim** — `## Operating procedure`'s *"do NOT run additional runQuerys to re-derive… the same figure"* — and the model obeyed the newer, more specific one. **The worked example was the sharpest part of the defect**: both halves of it are blueprint-covered in the seeded corpus (`bp-active-headcount-by-department`, `bp-average-salary-by-department`), so the illustration taught precisely the error. Fixed by narrowing rather than reverting: the bullet now leads with **never re-query to merge a blueprint result**, *citing* the authoritative-result rule instead of standing beside it; permits the merge only for parts being answered with the model's own SQL anyway; and routes the blueprint-answered case down the same exit as differing grains (primary table through the tool, the rest described in `answer`). The new example is drawn from `applicant_tracking_application`, and a contract test **checks against the corpus** that no blueprint `uses` that table rather than trusting the choice. The same unnarrowed text was in `ANSWER_WITH_TABLE_TOOL_SCHEMA["description"]`, which is re-sent every round-trip beside the prompt, and is narrowed identically. **The general lesson, and it is not about tables:** a new instruction must be written to land *inside* the instructions already present — added beside them, the more specific and more recent one wins, and the older rule is silently overridden while still passing its own test. → [01a §11](01a-prompt-draft.md)

    **⛔ The narrowing did not work either, and the whole rule is now REVERTED — see finding 26.** The measured 6/6-vs-1/9 gap above still stands and is still worth fixing; the fix is a multi-table `answerWithTable`, not a prompt rule.

25. **A turn that ran out of *enforcement* was recorded as having run out of *budget*.** 05 §F's fourth forced path — the budget cap reached **during a refused round** — wrote `BUDGET_EXHAUSTED`. Live (`s412e8424614e465bbd26d7a2a1400ebe` / trace `647416592aff2225d1903ae7c82b8396`): the answer was **computed at 25s**, the turn capped at **61.6s on the wall clock** (`max_wall_clock_seconds=60`, not tokens — tokens moved **+385 across the final three rounds**), and those 36 seconds went entirely to two rejected `updateAnalysisState` calls and one refused `answerWithTable`. Both intents were recorded `BUDGET_EXHAUSTED`, and **more budget would have changed nothing**. The cost of the wrong label is not cosmetic: it tells whoever reads [07 §E.2](07-evaluation.md)'s buckets a capacity story and sends them to raise a ceiling that is not the problem — the expensive kind of wrong, because acting on it feels like progress. Relabelled `ENFORCEMENT_EXHAUSTED` (*"enforcement could not establish a disposition"*), which is literally true here and in the ambiguous last-straw case. **One branch only:** the ordinary hard ceiling keeps `BUDGET_EXHAUSTED` (there the ceiling really is the cause) and the `"stop"` resume keeps `USER_STOPPED`; `RUNTIME_REASON_CODES` stays at three, so this is a relabel and not a new code. The capacity fact is not lost — it moves to `loop_intent_force_blocked.budget_cap_reached`, a bare `True` emitted on that path alone, so an operator still sees budget pressure while the ledger carries the honest cause. **The pattern worth reusing:** when a reason code has to become more honest and a real fact would be lost with it, move the fact to telemetry rather than overloading the code. → [05 §F.0](05-finalization-enforcement.md#f0-the-fourth-path-is-enforcement_exhausted-reversed-2026-08-12-on-measurement), [06](06-telemetry.md), [07 §E.2](07-evaluation.md)

26. **The same-grain merge rule was REVERTED outright after the narrowed version made the regression worse, not better — the instruction set it created was unsatisfiable, so no wording could have fixed it.** Finding 24 narrowed rather than reverted, on the theory that v1 failed because it was *unqualified* (absolute slogan, blueprint-covered worked example). Four live runs of one question — *"active headcount by department, average salary by department, and hires in the last 6 months"* — say otherwise: **pre-merge-rule** `runBlueprint ×3` → **3/3 intents completed**; **pre-merge-rule after the finding-22 `getBlueprint` gate** `runBlueprint ×2 + runQuery ×1` → **3/3 completed**; **v1** `runQuery ×3` → **timed out, no answer**; **v2 (narrowed)** `runQuery ×2` and **zero `runBlueprint`** → **timed out, no answer**. v2 was *worse than v1*: v1 at least still ran one blueprint. On the v2 run the model expanded all three blueprints via `getBlueprint` and then ran **none** of them, hand-writing a merged `SELECT department_name, COUNT(DISTINCT IF(employee_status …` twice — exactly the re-derivation v2's own leading clause forbids. **The `getBlueprint` gate is not the cause**, ruled out by isolation on the same build: a *single*-deliverable question ran `getBlueprint > runBlueprint > answerWithTable`, 3 calls, `done`. **Why sharper wording could not have saved it:** for a multi-part, blueprint-covered request three individually-correct rules cannot all hold — (a) one table per answer, because `answerWithTable` carries a single `sql`/`blueprint_id`; (b) never re-derive a blueprint result; (c) two blueprints each produce a table for two same-grain parts. (a)+(c) demands a merge, which breaks (b); (b)+(c) demands two tables, which breaks (a). The model resolves it the only way that satisfies all three formally — it **drops the blueprints**, so (b) has no object and one hand-written query serves (a) and (c). That is a coherent reading, not a misreading, which is why sharpening the text twice made it worse each time. **The fix is to dissolve premise (a): a multi-table `answerWithTable`**, scoped separately; the single-`sql` payload was a deliberate deferral and this is the measurement of what the deferral costs. **Kept, deliberately:** finding 19's separate table-rule fix (`This rule is UNCONDITIONAL` and the rescoped no-finalize bullet), which fixed a different real regression — 3 multi-row answers pasted into prose before, 0 after — and is independent of this rule. **The general lesson:** when a rule fails on measurement, the second question is not *"how do I word it better?"* but *"is what I am asking for satisfiable at all?"* — two rounds of rewording were spent before the conflict was written down, and writing it down took minutes. → [01a §§10–11 (both marked REVERTED)](01a-prompt-draft.md), and now [08](08-multi-table-answer.md), **built**.

27. **Two answer-table over-claims were live at N=1, and multi-table only made them unignorable.** Found building 08, verified against the code rather than taken from the brief. (a) `verification` was set by `_accumulate_enrichment` from **any** `runBlueprint` returning `status == "verified"` and never reset — `"passed": True` is still the only occurrence of that key in the runtime and there is no `passed: false` anywhere — so a turn that ran a verified blueprint for part 1 and then answered with a hand-written `runQuery` for part 2 rendered "verified ✓" over a grid nothing had checked. (b) `blueprint_use` had the same shape of problem one field over. Both are fixed by computing the envelope over the **designated tables**, which is a real behaviour change for existing single-table turns and is asserted rather than discovered. **The scoping matters as much as the rule:** the roll-up governs turns that designated a table; a verified blueprint answered in PROSE has no grid to over-claim on and keeps its badge, because downgrading it would delete the enrichment the approval-resume seed exists to carry across a pause — 08 §C.2 had already rejected that trade under a different name. **The general lesson:** when a field's meaning is widened, ask what it claimed at N=1 before assuming N>1 introduced the problem. → [08 §C](08-multi-table-answer.md)

28. **`_run_loop` accepted a seed kwarg and silently did not forward it, for as long as the kwarg has existed.** `seed_blueprint_terminal_sql` was built carefully by the blueprint approval-resume, declared on `_run_loop`'s signature, and then simply omitted from the `_run_loop_body(...)` call below it — so an `answerWithTable(blueprint_id=X)` naming the blueprint that completed BEFORE the pause resolved to nothing and the model was told "you have not run it this turn" about a blueprint it had run. The user lost the table on exactly the verified, approval-gated path the seed was written for. `_run_loop`'s own docstring argues that mirroring the full signature explicitly — rather than `**kwargs` — catches a typo'd kwarg at any of the three CALL sites; it does, and that is precisely why an omission at the single FORWARDING site was invisible. **Same class as findings 12, 18 and 20:** a mechanism that looked wired, passed its whole suite, and could not do the thing it was written for. Fixed with a regression test that fails without the forward. → [08 §N](08-multi-table-answer.md)

29. **The model never called `answerWithTable` on a multi-intent turn — and it was not a multi-table problem.** Measured on the build that shipped 08, three runs of one three-intent question: `answer_tables: 0` every time, 13 tool calls, all three intents `completed`, answer written as bullet-list prose. The obvious reading — the `tables` payload is too hard — is wrong, and the chains say so: the multi-intent turn ends `… runBlueprint@i3 > updateAnalysisState` and then writes prose, while a single-deliverable control on the *same build* ends `getBlueprint > runBlueprint > answerWithTable`. The model was not failing to send a multi-table answer; it was **not finalizing at all**. **Cause:** nothing ever told it that closing its last intent is not the end of the turn. `## Tracking a multi-part request` ends on *"Resolve every tracked intent before you finish"*, which reads as the last thing to do, and the terminal call lives in a section the model has no reason to return to. [05 §G](05-finalization-enforcement.md) had already worked out the correct shape — state calls dispatch first, so `updateAnalysisState` and `answerWithTable` can go in ONE response — but wrote it as an *enforcement affordance* and never said it to the model. **Same class as findings 12, 18, 20 and 28:** a mechanism that was wired, tested and correct, whose actor was never told it existed. Fixed by saying it in the tracking section, cross-referencing it from the table section, and mirroring it into both tool descriptions; the ceiling moved 15,000 → **16,000** to fit rather than deleting working instructions, per §7's own ruling. **The general lesson:** an affordance recorded in a design doc is not an instruction — if only the runtime knows a batch is legal, the model will pay the round-trip or, as here, simply stop. → [01a §13](01a-prompt-draft.md)

30. **`BudgetGuard`'s token ceiling is a per-window SUM of whole requests measured against a CONTEXT-SIZE number — so it binds at 6-14 rounds while the real context is 12-31% of the window.** Found while raising the wall clock (below); reported first, then **fixed the same day** — see the resolution at the end of this finding. `record_iteration(tokens_used=result.usage["total_tokens"])` (`agent_loop.py:3691`) adds the provider's **prompt + completion for that request**, and every request replays the whole conversation — so the counter accumulates `Σ context_k`, which is quadratic in round count, and it is compared against `max_tokens=model_context_window` (128k, `app.py:710`), which is an **occupancy** limit, not a spend limit. `budget_guard.py`'s own module docstring flags the substitution as *"a defensible default"*; it is defensible as an order of magnitude and wrong as a unit. **Measured** by driving the real loop and real assembly with a stub reporting request-sized usage: with a ~2.2k-token tool result per round the turn tripped the ceiling at **round 10** with the context at **24k tokens (19% of the window)** and the counter at **145k (113%)**; at a ~4.3k result it tripped at **round 8**, at ~7k at **round 6**, at ~765 tokens at **round 14**. In every case iterations (25) and wall clock were nowhere near. **Consequence for the budget raise:** `max_loop_iterations` is not the reachable round count — the token counter is — so a long multi-intent turn now pauses for a user "continue" at ~10 rounds instead of running to 25. **RESOLVED 2026-08-12 — spend got its own ceiling.** The two concerns the one counter conflated were separated rather than merged: **occupancy** (“will the next request overflow the window?”) is `max(context_k)` and was already enforced per-request by `fit_request_to_budget` against `request_token_budget()` (verified: at a 10.5k-token-per-result payload the last of 25 requests measured **89,229** against the 89,600 budget), so the guard was never protecting it; **spend** genuinely is `Σ(prompt + completion)`, so the *counting* was right and only the *comparison* was wrong. `BudgetGuard.max_tokens` → `max_token_spend`, fed by a new `RuntimeSettings.max_window_token_spend` = **1,000,000** (`max_loop_iterations` 25 × 40k mean request). Derived from measured FULL-25-round window spend on the same rig: 177k / 366k / **786k** / 1.35M / 1.61M / 1.86M at per-result sizes of 135 / 765 / **2,165** / 4,265 / 7,065 / 10,565 tokens — so the fattest *ordinary* payload runs all 25 rounds with ~27% headroom, while the *runaway* shapes (whose requests have plateaued against the fit budget and whose extra spend is re-sent context, not analysis) pause at ~round 21. Cached prompt tokens are counted at FULL weight — this is a runaway backstop, not a cost model, and the ~94% cache-read rate is priced into where the ceiling sits instead. → this file, and `docs/decisions/phase0-runtime-design.md` §11 OQ-H, which left the loop's token budget undefined

### Follow-up: pinning versus re-fetching (NOT done, deliberately)

Finding 23 makes the re-fetch *work*. It does not ask whether the re-fetch should have been necessary.

**What was observed.** `fit_request_to_budget` pins the K most recent current-turn tool pairs (`request_budget_pinned_recent_tool_pairs`, default 3) and drops older ones at tier 2. A long turn that fetches several schemas early and works from them later will therefore push the earliest schema out — and a schema is exactly the kind of context that is *cheap to keep summarised* and *expensive to re-acquire*, since re-fetching costs an MCP round-trip and re-adds the full payload the budget had just judged droppable. The new `loop_trimmed_read_refetch_capped` event exists to make this visible: **if it fires with any regularity, the re-fetch is treating a symptom.**

**Three shapes the real fix could take**, none of them attempted here: pin catalog reads (`getTableSchema`/`listTables`) the way the emulated-discovery pairs are already pinned by id (invariant 7); summarise a dropped schema to its column list instead of removing it, which is the compaction path `context/assembly.py` currently bypasses in this phase; or make the eviction cost-aware rather than purely recency-ordered.

**Why it was not done.** Each is a change to `fit_request_to_budget`'s *policy* — what context is worth keeping and at what cost — with effects on every turn, not just the thrashing ones. That is a deliberate design question with its own trade-offs (pinning shrinks the droppable pool, and the budget exists because that pool must not be empty), and it is not the sort of thing to change while fixing a guard. Recorded here rather than in a code comment so it is a decision with a rationale, not a TODO.

## The contract

> **For every intent the model chooses to track, Release 1 guarantees a recorded, falsifiable terminal disposition. It does not guarantee that every user intent was detected, nor that a model-declared disposition is semantically true.**

Approved by the Lead, 2026-08-11. Two separate problems with separate mechanisms: `analysisState` solves **state loss after detection**; the detection-rate metric (07 §E.3) measures whether the model created the state **in the first place**.

The same reasoning fixes how `ENFORCEMENT_EXHAUSTED` is described. It means **"enforcement could not establish a disposition"** — not that the system proved the intent impossible. Evidence that looks mechanical can be semantically ambiguous, so a code claiming proof would overstate what the runtime knows. Word it that way in `denial_mapping.py`, telemetry, and 07's report.

## Conventions these docs assume

**Test layout mirrors the module tree.** `tests/runtime/<package>/test_<module>.py`, with adversarial cases in a sibling `*_adversarial.py` or `*_qa.py` file — see `tests/runtime/loop/` for the established pattern.

**Degrade-not-fail, never silently.** Every new failure path emits an observer event and logs server-side; nothing reaches the model as `str(exc)`.

**The model-facing error channel is `denial_detail`, not `user_message`.** `context/budget.py::_render_entry` builds it from the persisted entry — `denial_detail` if set, else `classify_denial(error_code)` — never from `ToolResult.user_message`, which has no `TrailEntry` field. A specific message set only on `user_message` is silently dropped. Every new error code needs a `denial_mapping.py` entry *and*, where the text must name specifics, a `denial_detail`.

**Telemetry is shape-only** (D25): counts, enums, tool names. Never question text, SQL, cell values, or resolved code strings.

**Provenance for tools that read no warehouse data is `frozenset()`, not `None`.** `None` means *undetermined* and is dropped fail-closed from replay — see the long note in `composite/record_assumptions.py` for what that cost when it was got wrong.

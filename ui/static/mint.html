Author a blueprint

Describe a question you already know how to answer. This drafts a blueprint from it and files it on the review queue — it does not publish anything. You review the draft there, trial-run it, and approve it like any other candidate.

The question

What should this blueprint answer? Write it the way someone would ask it.

Tables

Pick the tables to answer it from. The draft is grounded on their columns — an unselected table cannot be read, and its columns cannot be cited.

Steps

How you would answer it, in order. These shape the query; they are not stored as a separate field, so anything that changes what the number MEANS belongs in an assumption or the question itself.

Shape

Most blueprints are one query. Choose several steps when a later step needs an earlier step's result — a ratio against a total, a rollup over a per-employee table. You declare the steps and which feeds which; the assistant only writes the SQL, because a model guessing the dependency edges produces a graph nothing can check.

A step passes on either one value (a total, an average) or its whole result set (choose "a table" when many rows flow onward). The wiring notation is generated for you — the assistant writes {name} for a single value, or reads scratch.name for a table.

Assumptions

What has to be true for the answer to be right — "excludes terminated employees", "earnings only, not deductions". Ones that change the meaning of the number are folded into the blueprint's intent.

SQL

If you have a query that ran, say so — it is used verbatim and the assistant is given no way to rewrite it. A sketch is corrected and completed instead.

A multi-step blueprint is built from its steps, so each step carries its own query — write them in the Shape section above. There is no whole-query box for a DAG.

This may already exist

A warning, not a block — the same question at a different grain is a real blueprint of its own. Check these before approving your draft.
